# harness-evolve — 프로젝트 하네스 자가 개선

프로젝트 지침 문서는 고칠 때마다 조금씩 늘어나는데, 고친 것이 효과가 있었는지는 아무도 확인하지 않는다. 이 스킬은 반대 방향으로 돈다. 실제 작업 기록에서 문제가 **관찰된** 곳만 찾고, 한 번에 **하나만** 고치고, 다음 회고 때 그 변경이 **예측대로 작동했는지** 확인해 유지하거나 되돌린다.

## 범위

| 고치는 곳 (승인 후) | 고치지 않는 곳 (발견으로만 보고) |
|---|---|
| `agent-guide/GUIDE.md` · `PROJECT.md` · `SESSION.md` | 전역 지침 (`~/.claude/CLAUDE.md`·`rules/`, `~/.codex/AGENTS.md`, agy 전역 지침) |
| 프로젝트 루트의 `CLAUDE.md`·`AGENTS.md` 진입 링크 | 스킬, 에이전트 정의, 메모리, `init-project` 템플릿 |
| `agent-guide/retro-log.md` (이 스킬의 기록) | 제품 코드 |

전역 지침은 모든 프로젝트와 세 도구에 함께 걸린다. 한 프로젝트의 기록만 보고 거기를 고치면 다른 프로젝트에서 무슨 일이 생길지 알 수 없다. 원인이 전역 쪽에 있어 보이면 그렇다고 보고만 한다.

## 세 문서의 자리

GUIDE는 루트 `CLAUDE.md`·`AGENTS.md` 링크로 **매 세션 자동으로** 읽힌다. PROJECT와 SESSION은 `start` 스킬이 읽는다. 그래서 무엇을 어디에 둘지가 비용과 효과를 가른다.

| 문서 | 담는 것 | 판단 기준 |
|---|---|---|
| GUIDE | 이 프로젝트에서 **일하는 방식**: 관례, 금지, 완료 기준, 용어 | 매 세션 읽힐 가치가 있는가. 사실이나 상태는 넣지 않는다 |
| PROJECT | **사실**: 구조, 코드 지도, 명령, 환경, 경로 | 지금 실제와 맞는가 |
| SESSION | **상태**: 다음 작업, 이력 색인 | `update-docs` 형식을 따른다 |

자리를 잘못 잡은 내용(GUIDE에 들어간 경로 목록, PROJECT에 들어간 작업 원칙)은 그 자체로 발견이다.

## 절차

### 1. 지난 회고 확인

`agent-guide/retro-log.md`가 있으면 먼저 읽는다.

- **관찰 중** 항목마다 적어 둔 예측(바뀔 행동·지킬 행동)을 이번 기록과 대조해 유지·되돌림·판단 보류 중 하나를 제안한다. 관련 작업이 기록에 없으면 판단 보류다. 예측이 틀렸는데 유지하자고 하지 않는다. 이 확인이 이 스킬의 핵심이다.
- 마지막 회고 날짜를 이번 기록 범위의 시작점으로 쓴다.

### 2. 기록 모으기

재료는 두 가지다.

- **지금 대화**: 세션 끝에 부르면 가장 좋은 재료다. 사용자가 무엇을 정정했는지, 어디서 막혔는지가 그대로 있다.
- **세션 기록 요약**: 이전 세션이나 도구별 기록은 스크립트로 요약한다. 원문 jsonl은 수 MB라 직접 읽지 않는다.

```bash
S=~/.claude/skills/harness-evolve/scripts/session_digest.py
python3 $S --list                          # 이 프로젝트의 세션 목록 (프로젝트 루트에서 실행)
python3 $S --since 2026-09-01              # 지난 회고 이후 세션 전부
python3 $S --last 3 --no-timeline          # 최근 3개, 집계만
python3 $S --session <jsonl> --max-lines 600   # 특정 세션의 흐름을 길게
python3 $S --session <jsonl> --conversation    # 도구 호출 없이 사용자·에이전트 대화만
```

정정을 찾았으면 `--conversation`으로 그 앞뒤를 읽는다. 사용자가 무엇을 바로잡았는지는 직전에 에이전트가 무엇을 보고했는지를 봐야 알 수 있다.

요약에는 사용자 메시지, 도구 호출 흐름, 지침 문서 읽기, 읽기만 한 파일과 고친 파일, 반복 읽기·검색, 실패한 호출, 중단이 나온다. 셸 명령의 읽기·검색 구분과 묶음 명령의 크기 배분은 추정치다. agy 기록은 지원하지 않으니 대화로만 본다. 기록이 하나도 없으면 그렇게 말하고, 문서와 실제 파일의 대조 같은 정적 점검만 한다.

`--list`에는 상위 경로(예: `/workspace`)에서 열었지만 이 프로젝트를 다룬 세션도 "상위 경로"로 나온다. 사용자가 여러 프로젝트를 한 자리에서 오가며 일하면 중요한 정정이 이런 세션에 들어 있다. 언급이 많은 것부터 `--session`으로 요약해 이 프로젝트 부분만 본다. 오래된 기록도 날짜만 보고 빼지 않는다. 그때의 정정이 지금 문서에 반영돼 있는지 대조하는 것 자체가 발견이 된다.

기록이 쓰인 뒤에 문서가 바뀌었을 수 있다. `git log --since=<기록 날짜> -- agent-guide/`로 확인하고, 이미 고쳐진 문제는 발견에서 뺀다.

### 3. 발견 뽑기

| 무엇 | 기록에서 보이는 모습 | 고칠 자리 |
|---|---|---|
| 사용자 정정 | 같은 지적이 되풀이되거나, 사용자가 프로젝트 관례를 직접 알려 줌 | GUIDE에 없으면 누락, 있는데 안 지켰으면 문구 문제 |
| 탐색 헛걸음 | 코드 지도에 없는 파일을 찾느라 검색을 반복, 같은 파일을 여러 번 읽음 | PROJECT 코드 지도 |
| 환경 오인 | 문서가 말하는 실행 위치(어느 장비, 컨테이너 안인지 밖인지)가 지금 체크아웃과 다름. `hostname`, `/.dockerenv` 등으로 직접 확인 | 해당 문서 |
| 낡은 사실 | 문서의 경로·명령이 실제와 다름 (직접 `ls`·`git`으로 확인) | PROJECT |
| 반복 실패 | 같은 명령이 같은 이유로 거듭 실패 | PROJECT 명령 표 |
| 안 쓰이는 적재 | 매번 읽히는 GUIDE·SESSION 구간이 검토한 작업 어디에도 쓰이지 않음, 전역 지침과 같은 말 | 빼기 후보 |
| 구조 | 루트 진입 링크가 없거나 깨짐 | 링크 |

정정은 **주제로 묶어** 센다. 세부 내용이 달라도 원인이 같으면 같은 정정의 반복이다. 예를 들어 한 세션에서는 캐시 만료 정책을, 다른 세션에서는 재시도 횟수를 결함으로 보고했다가 둘 다 "일부러 그렇게 한 것"이라고 정정받았다면, 두 번의 "의도된 설계를 결함으로 오인"이다. 하나씩 따로 세면 전부 1회짜리 약한 근거로 흩어져 가장 강한 신호를 놓친다.

"읽기만 한 파일"은 헛걸음이 아니다. 참고하려고 읽었을 수 있으니 대화 흐름으로 판단한다. 발견마다 원인이 어디에 있는지 정한다: 프로젝트 문서, 전역(보고만), 모델의 일회성 실수(조치 없음). 회고 중에 제품 코드나 설정 파일의 실제 결함을 보면 고치지 않고 발견 표에 "범위 밖"으로 남긴다.

### 4. 하나 고르기

발견이 여러 개여도 제안은 하나다. 한 번에 여러 곳을 고치면 다음 회고 때 무엇이 효과를 냈는지 가를 수 없다. 나머지는 발견 표에 남긴다. 고를 때 아래를 거친다.

- **근거 강도**: 사용자가 정정했거나 2개 이상의 작업에서 되풀이된 것만 제안한다. 한 번 본 헛걸음은 우연일 수 있으니 retro-log에 관찰로만 남긴다.
- **빼기 먼저**: 기존 문구를 고치거나, 지우거나, 자리를 옮겨서 풀리면 그게 먼저다. 추가는 마지막 수단이다.
- **사건 맞춤 문구 금지**: GUIDE에 넣을 문장에 이번 사건의 파일명·날짜·오류 문자열이 들어가면 그 사건에만 맞춘 것이다. 원칙으로 일반화하거나, 사실이면 PROJECT로 보낸다.
- **중복**: 같은 내용이 전역 지침이나 다른 문서에 이미 있는지 확인한다. 전역과 같은 말이면 프로젝트 쪽을 지우는 것이 후보다.
- **크기**: 늘고 주는 줄 수를 적는다. GUIDE는 매 세션 읽히므로 늘리는 쪽에 엄격하다.
- **예측**: 행동을 바꾸려는 변경이면 바뀔 행동 하나, 그대로여야 할 행동 하나, 다음 회고 때 확인할 방법을 적는다. 낡은 경로 정정처럼 사실을 맞추는 변경은 대조로 끝나니 예측이 필요 없다.

고칠 것이 없으면 "변경 없음"이 결론이다. 억지로 만들지 않는다.

### 5. 보고하고 승인 받기

승인 전에는 어떤 파일도 고치지 않는다.

```
## 🔍 회고 범위
세션 N개 (도구, 기간) · 지난 회고 이후 문서 변경 여부

## ⏪ 지난 변경 확인        ← retro-log에 관찰 중 항목이 있을 때만
| 변경 | 예측 | 이번 기록 | 제안 (유지/되돌림/보류) |

## 📋 발견
| # | 무엇 | 근거 (세션·U번호·시각) | 강도 | 원인 위치 |

## 💡 제안
- 대상: 파일과 위치
- 변경: 바꾸기 전과 후 (짧은 diff)
- 왜 이것인가, 빼기로 안 되는 이유
- 예측: 바뀔 행동 / 지킬 행동 / 확인 방법   ← 사실 정정이면 생략
- 크기: +a −b줄

반영할까요?
```

### 6. 승인 후

1. Edit로 반영한다.
2. `agent-guide/retro-log.md`에 항목을 추가한다. 지난 변경의 판정도 같은 파일에 적는다.
3. 커밋하지 않는다. 커밋은 사용자가 따로 요청할 때만 한다.

## retro-log.md 형식

회고마다 한 항목. 새 항목을 위에 쓴다. 이 파일은 `start`가 읽지 않으니 세션 시작 비용이 들지 않는다.

```markdown
# 지침 회고 기록

## 2026-10-12 · GUIDE "완료 기준" 절에 시험 명령 위치 안내 — 관찰 중
- 검토: codex 2026-10-05~10-11 세션 3개
- 근거: 10-08 U4, 10-10 U2 — 사용자가 E2E 대신 단위 시험을 돌린 것을 두 번 정정
- 바뀔 행동: 화면 작업 완료 전에 `npm run test:e2e`를 돌린다
- 지킬 행동: 화면과 무관한 작업에서는 E2E를 돌리지 않는다
- 확인: 다음 회고 때 화면 작업 세션에서 E2E 실행 여부
- 크기: +1줄
- 결과: (다음 회고에서 채움)

## 2026-10-05 · 변경 없음
- 검토: claude 10-01~10-04 세션 2개
- 관찰: `scripts/` 탐색이 한 번 길었음 (근거 약함, 다음에 다시 보면 제안)
```

상태는 `관찰 중`, `유지`, `되돌림`, `판단 보류`, `정정 완료`(사실 정정) 중 하나다.

## 멈출 때

- 발견과 변경을 기록으로 이어 붙이지 못하면 제안하지 않는다.
- 검토한 기록에 관련 작업이 없으면 지난 변경의 판정을 보류한다. 효과가 없다고 단정하지 않는다.
- 회고가 문서를 늘리는 쪽으로만 연달아 가면, 다음 회고는 빼기 후보부터 본다.
