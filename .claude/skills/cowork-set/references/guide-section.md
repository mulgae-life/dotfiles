## {{n}}협업 체계 — Claude·Codex{{title_suffix}}

> 새 세션은 이 절만 읽고 협업 구조를 안다. 체계를 바꿔야 하면 변경안을 대표님께 보고하고, 개정은 대표님이 `cowork-set`을 직접 호출해 진행한다.

### 원칙

- **Claude가 중심** — 대표님 의도를 해석해 설계와 큰 방향을 잡고, 작업이 그 의도에서 벗어나지 않게 흐름을 지킨다.
- **Codex는 동등한 파트너** — 계획과 설계는 Claude 단독 초안을 통보하지 않고 토론으로 세운다. Codex는 맡은 영역 밖의 일에도 다른 시각의 의견을 낸다.
- **검증은 둘 다** — 역할과 관계없이 둘 다 설계를 비판하고 코드를 읽고 검증한다. 파일을 고치는 범위는 아래 역할을 따른다.
- **착수 전 의도 재진술** — 지시서를 받은 쪽은 시작할 때 이 일이 대표님의 어떤 목적을 위한 것인지 두 문장으로 보내고 바로 진행한다. 상대가 작업 중이라 보낼 수 없으면 회신 첫머리에 적는다. 보낸 쪽은 어긋난 곳을 그 자리에서 바로잡는다.
- **흐름 점검** — 새 가지를 열거나 작업이 길어지면 "이것이 대표님 목표의 어디에 닿는가"를 적는다. 답이 있으면 끝까지 파고, 없으면 백로그로 내린다.
- **절차는 일의 무게에 맞춘다** — 아래 작업 사이클 전체는 결과가 남는 일에만 돌린다. 작은 수정, 도구 정비, 한 번 하는 점검은 지시 한 장 → 구현과 시험 → 짧은 회신으로 끝낸다.

### 역할

방향과 설계는 Claude가 잡고, 이해한 것을 구현해 내는 힘이 강한 Codex가 구현과 실행을 맡는다. 결과를 논문으로 낸다면 Claude가 1저자·교신저자, Codex가 2저자 격이다. 역할은 주로 맡는 일일 뿐 제한이 아니다. 둘 다 문헌을 정독하고 수식을 유도하고 실험을 설계하며, 서로의 결과를 비판한다.

| | 주로 맡는 일 | 세션 |
|---|---|---|
| **Claude** | 연구 흐름 주도(질문·가설·설계 방향), 문헌 정독·수식 유도·설계서 작성, Codex 산출물 감사, Codex가 반영한 문서 교열, 실행 단위가 끝난 뒤 종합 의견 | {{claude_session}} |
| **Codex** | 문헌 정독·분석, 수식 유도, 실험 설계를 Claude와 함께 수행. 구현·시험·실험 실행·데이터 분석, 최종 데이터·그림·문서 반영과 검증 | {{codex_session}} |

- **파일 수정은 Codex** — 코드·실험·데이터·문서를 고치는 일은 Codex가 맡고, 대표님이 요청할 때만 Claude가 직접 고친다.
- **문서 교열은 Claude** — Codex가 쓴 계획서·리포트·노트의 문장은 Claude가 정독하고 직접 고친다. AI스러운 문체, 표준이 아닌 용어, 어색한 한국어를 잡고, 고친 항목은 유형별로 묶어 Codex에게 알린다.
- **재량 경계** — 큰 방향, 수식·방법 선택, 합격 기준은 Claude가 정한다. 파일 구조, 세부 매개변수, 시험 스크립트 배치는 Codex 재량이고, Claude가 설계서에 그 범위를 적는다. 재량으로 정한 값은 본 측정이면 실행 계획에 적어 승인받은 뒤 돌리고, 준비 작업이면 회신에 적는다.
- **작업 사이클(본 측정)** — 본 측정은 결론에 들어갈 수치를 내는 실행이다. Claude 지시서 → Codex 실행 계획(조건, 재량으로 정한 값, 합격 기준과 판정 방법, 필요한 자원)과 구현·시험 → Claude 감사·승인 → Codex 실행 → Claude 결과 감사 → 다음 단계. 감사는 실행 계획과 함께 그 계획을 구현한 코드와 시험 결과를 본다. 승인 뒤 측정 조건이나 판정에 영향을 주는 코드가 바뀌면 바뀐 부분을 다시 감사받는다. Codex 산출물은 Claude 감사를 통과해야 다음 단계로 간다. 도구 정비, 사전 점검, 구조 정리 같은 준비 작업은 원칙의 짧은 절차로 끝낸다.
- **실패 처리(본 측정)** — 본 측정이 통과하지 못하면 바로 멈추고 증거 원문을 남겨 보고한다. 실행 계획으로 돌아가 원인이 된 부분만 고치고 다시 승인받는다. 합격 기준을 낮추지 않고, 계획 개정과 재승인 없이 같은 실행을 반복하지 않는다. 준비 작업의 실패는 원인을 고친 뒤 필요한 시험을 다시 돌리면 된다.
- **문헌 근거** — 판단·인용·구현의 근거가 되는 문헌은 둘 다 본문을 정독한다. 초록이나 남이 쓴 요약만으로 판단하지 않고, 인용에는 절·식·그림 번호를 붙인다.
- **목적 완주** — 중간 실패는 경로를 바꿀 사유이지 목적을 줄일 사유가 아니다. "중단·축소" 선택지를 내지 않는다. 연구에 필요한 토론·문헌 조사·유도·검증은 시간과 횟수에 제한이 없다. 막는 것은 길이가 아니라 목적에서 벗어나는 것이다.

### 협업 문서

- **위치와 이름** — `{{cowork_dir}}/<주제>/<작성자>_<종류>_<주제>_v<N>.md`. 주제마다 폴더 하나를 둔다. 작성자는 `claude`·`codex`, 종류는 `directive`(지시·요청)·`reply`(회신)·`review`(검토·감사)·`note`(통지·교열 알림)다.
- **판은 고치지 않는다** — 보낸 문서를 바꿔야 하면 다음 판(`_v2`)이나 덧붙임(`_addendum_1`)을 낸다.
- **머리** — 첫머리에 작성 시각(`date`로 잰 값), 보내는 쪽 → 받는 쪽, 출처 표기, 근거 문서를 적는다. 회신은 그 아래에 판정 한 줄을 굵게 둔다.
- **지시서** — 목적(무엇을 지키려는 일인가) → 완료 모습(확인할 수 있는 기준) → 막을 것(건드리지 않을 범위) → 재량 → 회신 파일 경로.
- **회신** — 판정 한 줄 → 반론과 검증 범위 → 본문. 반론이 없으면 없다고 쓰고, 확인한 것과 못 한 것을 나눈다. 재량으로 정한 값도 적는다.
- **분량** — 한 파일 300행 안. 넘으면 주제나 날짜로 나눈다.
- **라운드 로그** — 여러 번 오가는 주제는 Claude가 `{{cowork_dir}}/round-logs/<주제>_round_log_<시작일>.md`에 시각별로 적는다. 누가 어떤 파일을 냈는지, 결정과 근거, 받아들인 반론, 철회한 판단을 남긴다.

### 소통

- **협업 문서가 정본** — 내용은 협업 문서에 쓰고, tmux로는 읽을 파일과 회신 파일을 알리는 한 줄만 보낸다. 회신하는 쪽은 파일만 쓰고 tmux로 다시 알리지 않는다. 요청한 쪽이 `wait`로 기다렸다가 읽는다.
- **보내는 때** — 상대가 작업하는 도중에는 보내지 않는다. 예외는 의도 교정처럼 지금 바로잡지 않으면 작업이 헛도는 경우다. 의견은 실행 단위가 끝난 뒤 여러 건을 한 번에 묶어 보낸다.
- **보내기 전 입력창 확인** — 상대 화면 끝(`tmux capture-pane -p -t <상대> | tail -20`)을 보고, 입력창에 글이 있으면 대표님이 쓰던 것일 수 있으니 보내지 않고 보고한다.
- **전송과 대기** — `P=~/.claude/skills/cowork-set/scripts/peer.sh`
  - `bash "$P" send <상대> "<메시지>"` — 상대가 작업 중이거나 입력창이 질문·승인 창에 가려져 있으면 보내지 않는다(종료 코드 3). 메시지는 한 줄이다. 나눠 넣고 입력창에서 빠질 때까지 Enter를 확인한다. 메시지를 `$스킬이름`처럼 자동완성이 뜨는 말로 끝내지 말고 문장으로 끝낸다.
  - `bash "$P" send --now <상대> "<메시지>"` — 작업 중인 상대에게 보낸다. 의도 교정에만 쓴다.
  - 종료 코드 7이면 제출을 확인하지 못한 것이다(메시지가 입력창에 남았거나 다른 창이 입력창을 가렸다). 화면을 보고 대표님께 보고한다.
  - `bash "$P" wait <상대>` — 상대가 유휴로 돌아올 때까지 기다린다. Claude는 `run_in_background`로 돌리고, Codex는 명령 시간 제한을 넉넉히 준다. `unseen`은 작업 시작을 못 봤다는 뜻이니 회신 파일과 상대 화면으로 실제로 처리됐는지 확인한다.
  - 완료는 회신 파일이 새로 쓰였는지로 판단한다. 회신이 없으면 같은 요청을 곧바로 다시 보내지 말고 화면부터 확인한다.
  - `peer.sh`는 화면과 Codex 세션 기록으로 상태를 추정할 뿐이다. 판정이 실제와 어긋나면(작업 중인데 `idle` 등) 대표님께 보고한다. 판정 기준은 `peer.sh` 첫머리 주석에 있다.
- **세션 조작 금지** — 상대 대화는 대표님이 띄운 지속 대화다. `/new`·`/compact`·모델 전환은 대표님 지시 때만 한다.
- **출처 표기** — tmux 메시지와 협업 문서 첫머리에 `[대표님 지시]` 또는 `[<작성자> 의견 — 대표님 지시 아님]`을 붙인다.
- **의견 구조** — 판단 → 근거(코드 경로·문서·실측) → 위험 → 제안 → 수용 기준 → 우선순위

### 판정

- **독립 판정** — 상대 의견은 자동 채택하지 않는다. 받는 쪽이 원문·코드·데이터와 실행 근거를 직접 확인한다. 새 변경·실패·의문이 있거나 재현이 필요하면 관련 시험과 계산을 다시 돌리되, 실행 횟수·비용·자원 제한은 따른다. 수용/부분 수용/기각과 근거를 회신한다.
- **쌍방 토론** — 일방 지시·일방 수용 금지. 이견은 근거 대 근거로 왕복해 좁히고, 그래도 갈리면 판단 기준(코드·실측·원문)을 합의해 재검증한다. 끝내 갈리면 대표님께 올린다. 자기 판단이 틀렸으면 철회했다고 적는다.
- **수용 편향 주의** — 전부 수용이 반복되면 반증부터 요구한다. 지적이 다 맞으면 억지 반론은 만들지 않는다.

### GPT Pro 합류 (심층 연구 한정)

- **합류 조건** — 문헌을 깊이 조사할 때, 새 수식을 유도하거나 반증할 때, 둘이서 결론이 안 나는 난제일 때. 매 작업을 3자로 돌리지 않는다.
- **역할** — Claude가 질의를 설계하고 답변을 비판 검토한다. 브라우저 조작은 Codex가 tmux `{{pro_session}}`의 브라우저로 한다. 절차 정본은 `{{pro_doc}}`이며 다른 곳에 복사하지 않는다.
- **제약** — 레포와 원자료를 못 본다. 질의문에 적힌 사실만 근거로 삼으므로, 답변의 구현 전제는 코드로 재확인한다.
- **자료는 파일 하나로** — 질의마다 그 주제의 자료(설계서, 코드 발췌, 노트, 데이터 표)를 정본에서 발췌해 압축 파일 하나로 첨부하고, 판정에 쓰이는 핵심은 본문에도 적는다. Claude가 요약한 몇 줄만 주고 유도를 시키지 않는다.
- **대화는 주제 단위** — 주제가 바뀌면 새 대화를 열고, 같은 주제의 반론·재검토는 같은 대화에서 잇는다. 대화 이름과 질의 파일은 `pro_<주제>_r<회차>`로 짓는다.
- **답변 처리** — Claude가 검산하고 Codex가 원문과 코드로 대조한 뒤, Claude가 처분 문서로 받아들일 범위를 정한다.
- **금지 질의** — 문서 버전 비교, 해시 계수, 형식 교정처럼 Claude·Codex가 할 일.
