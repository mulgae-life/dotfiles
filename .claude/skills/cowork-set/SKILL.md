# cowork-set — 협업 체계 세팅

- 대표님이 한 번 불러 세팅하면 끝나는 스킬이다. 이후 협업 규칙의 정본은 GUIDE의 "협업 체계" 절이다.
- 루트 `CLAUDE.md`·`AGENTS.md`가 GUIDE 링크라 새 세션은 두 도구 모두 협업 절을 자동으로 읽는다. 이미 떠 있는 상대 세션은 3단계에서 맞춘다.
- Claude는 `/cowork-set`, Codex는 `$cowork-set`으로 부른다. **호스트**는 스킬을 실행한 쪽, **상대**는 다른 쪽이다.
- **중심**은 대표님이 주로 대화하며 지시하는 쪽, **파트너**는 다른 쪽이다. 어느 도구든 중심이 될 수 있고, 호스트가 중심일 수도 파트너일 수도 있다.

## 분기

| 상태 | 할 일 |
|------|------|
| `agent-guide/GUIDE.md` 없음 | 중단하고 `/init-project`를 먼저 안내 |
| 협업 절 없음 | 1~4단계 |
| 협업 절 있음 (`grep -nE '^## .*협업 체계' agent-guide/GUIDE.md`) | 현재 역할 배분을 요약해 보여 주고 개정할지 묻는다. 개정이면 1~4단계를 밟되 2단계에서 바뀐 줄만 고친다 |

## 1단계: 정하고 확인받기

- **중심** — 대표님 말씀이나 기존 협업 절로 정해져 있으면 그대로 따른다. 정해진 것이 없으면 Claude를 제안한다. 제품형은 UI·디자인 품질에서 Claude가 앞서 구현까지 맡는 편이 낫고, 연구형은 구현해 내는 힘이 강한 Codex가 실행을 맡는 편이 낫다고 보기 때문이다. 스킬을 부른 쪽이 중심이라고 단정하지 않는다.
- **유형** — PROJECT.md와 코드에서 추정한다.

  | 유형 | 신호 | 배분 |
  |------|------|------|
  | 제품형 | 프론트엔드 프레임워크(`package.json`의 react·next·vue·svelte 등), UI 컴포넌트, 웹 서비스 | 설계·구현 중심, 검수(설계서 검토·코드 리뷰·E2E·QA) 파트너 |
  | 연구형 | 수치 계산·시뮬레이션·실험·데이터 분석 코드, 논문·노트 | 연구 흐름·설계·감사·교열 중심, 구현·실험·분석·문서 반영 파트너 (문헌 정독·유도·실험 설계는 함께) |
  | 혼합형 | 두 성격이 영역별로 섞임 | 영역마다 구현 주체를 나눔 |

- **유형별 세부** — 제품형은 파트너가 고칠 테스트 경로, 혼합형은 영역별 경로와 구현·검수 주체. 모르면 `[TODO]`.
- **세션**
  - 상대: `tmux ls`로 찾는다. 없거나 후보가 여럿이면 묻고, 대신 띄우지 않는다.
  - 호스트: `$TMUX`가 있으면 `tmux display-message -p -t "$TMUX_PANE" '#S'`, 없으면 tmux 밖. `$TMUX` 없이 `display-message`를 부르면 다른 세션 이름이 나온다.
- **협업 문서 위치** — 기본 `agent-guide/cowork/`. 프로젝트에 협업 산출물 자리가 이미 있으면 그것을 쓴다.
- **GPT Pro 합류** — 반드시 묻는다.
  - 문헌을 깊이 조사하거나 새 수식을 유도·반증하는 연구가 아니면 넣지 않기를 추천한다.
  - 넣으면 브라우저 조작 절차 문서와 브라우저 tmux 세션이 있는지 확인한다. 이 서버에서는 `/workspace/CFD/agent-guide/docs/CHATGPT_PRO_BROWSER.md`와 `codex-pro-browser`이고, 없으면 묻는다.

정한 내용을 한 번에 보여 주고 확인받는다.

```
📋 협업 체계안
- 중심: Claude (근거: 대표님이 Claude 세션에서 지시)
- 유형: 제품형 (근거: package.json에 next, app/ 아래 UI 컴포넌트)
- Claude: 요구 해석, 설계, UI·디자인, 구현 — tmux dot
- Codex: 설계서 검토, 코드 리뷰, E2E·QA — tmux dot-codex, 테스트 코드(e2e/)만 수정
- 협업 문서: agent-guide/cowork/<주제>/
- GPT Pro: 넣지 않음
```

## 2단계: GUIDE에 협업 절 넣기

- `references/guide-section.md`의 변수를 채우고 정한 블록만 남긴다.
- 처음이면 GUIDE 끝에 추가한다. 절 번호를 쓰는 GUIDE면 다음 번호를 붙인다.
- 개정이면 기존 협업 절 안에서 바뀐 줄만 고친다.
- 협업 절 밖은 고치지 않는다.

## 3단계: 상대 세션에 역할 확인받기

호스트가 중심이면 파트너 입력창에 요청을 넣고 신호로 회신을 받는다.

1. 상대 화면 끝을 본다(`tmux capture-pane -p -t <상대> | tail -20`). 입력창에 대표님이 쓰던 글이 있으면 건드리지 말고 보고한 뒤 멈춘다.
2. 알림을 보내고 수신기를 띄운 뒤, 신호를 받으면 회신을 읽는다. 종료 코드의 뜻은 `peer.sh` 사용법에 있다.

   ```bash
   P=~/.claude/skills/cowork-set/scripts/peer.sh
   bash "$P" send <상대> "[대표님 지시] agent-guide/GUIDE.md의 '협업 체계' 절을 읽고, 주로 맡는 일과 고칠 수 있는 범위, 상대가 맡는 일을 세 줄로 회신한 뒤 그 절의 signal 명령으로 알려 주세요."
   bash "$P" listen <신호 이름>   # Claude는 run_in_background로 띄우고, Codex는 끝날 때까지 출력을 다시 조회하며 기다린다
   # 신호를 받은 뒤
   tmux capture-pane -p -t <상대> -S -60 | tail -40
   ```

   - `send`가 종료 코드 3이면 상대 화면을 본다. 작업 중이면 `wait` 뒤에 다시 보내고, 질문·승인 창이 떠 있으면 대표님께 보고한다.
3. 회신이 협업 절과 어긋나면 어긋난 줄만 짚어 다시 확인받는다.

호스트가 파트너면 중심 대화창에 글을 넣지 않는다. 1~2 대신 신호를 남기고 중심의 답을 기다린 뒤, 3은 그대로 한다. 신호를 남기고 `wait`로 기다리는 것은 중심이 자기 화면에 답하는 이 확인에만 쓴다.

```bash
P=~/.claude/skills/cowork-set/scripts/peer.sh
bash "$P" signal <신호 이름> "[<호스트> 신호] [대표님 지시] agent-guide/GUIDE.md의 '협업 체계' 절을 읽고, 주로 맡는 일과 고칠 수 있는 범위, 상대가 맡는 일을 세 줄로 답해 주세요."
bash "$P" wait <상대>
tmux capture-pane -p -t <상대> -S -60 | tail -40
```

- `signal`의 종료 코드 0은 수신기가 신호를 읽었다는 뜻일 뿐이다. 역할 확인은 중심의 답을 읽고 판단한다.
- 종료 코드 8이면 중심이 수신기를 띄워 두지 않은 것이다. 중심이 Codex면 유휴일 때는 수신기가 없는 것이 정상이다. `wait`로 넘어가지 말고, 4단계에서 역할 확인이 남았다고 보고하며 중심 세션에 협업 절을 읽혀 달라고 대표님께 요청한다.
